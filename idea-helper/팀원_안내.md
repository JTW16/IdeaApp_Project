## 1. 시연 가이드

### ⚠️ 먼저 알아둘 것: Gemini 사용량 · 크레딧

10-19부터 Gemini API는 **유료 1등급(선불 크레딧, 자동 충전 꺼짐)**이라 하루 한도 걱정은 없습니다.

- 비용: 아이디어 1회 약 ₩10, 만드는 법 1회 약 ₩30. 리허설 + 시연을 합쳐도 ₩100~200 정도
- **발표 며칠 전에 AI Studio에서 크레딧 잔액만 확인**합니다. 잔액이 0이 되면 AI 생성이 실패합니다(앱에 한도 안내나 오류 문구가 뜸)
- 같은 조합은 AI를 부르지 않으므로(DB에서 꺼냄) 크레딧을 쓰지 않습니다
- (참고) 결제가 없는 키라면 무료 등급이라 모델당 하루 20회까지만 됩니다. 한도는 한국 시간 오후 4~5시쯤 초기화

### 서버는 어디서 · 어떻게 여나

**발표에 쓰는 노트북에서 직접** 켭니다. 서버를 따로 빌릴 필요는 없습니다.
노트북에서는 서버와 앱 두 개만 돌고, DB(Supabase)와 AI(Gemini)는 이미 인터넷에 있습니다 → **인터넷만 되면 어느 노트북이든** 됩니다.

```
발표 노트북
 ├ 서버 (localhost:4000)  ──인터넷──▶ Supabase (DB, 서울) · Gemini (AI)
 └ 앱   (localhost:8081)  ◀── Chrome으로 열어서 화면 공유 · 프로젝터
```

청중이 **자기 휴대폰으로** 앱이나 공유 링크를 직접 열게 하려면 서버를 클라우드(Render 등)에 올려야 합니다. 발표자 화면으로만 시연하면 필요 없습니다.

### 발표 노트북 준비 (전날까지, 한 번만)

지금 개발한 PC가 아닌 노트북으로 발표한다면 미리 해 둡니다. 당일에 하면 `npm install`만 몇 분 걸립니다.

1. Node.js 20 이상, Git, Chrome 설치
2. 저장소 받기 (비공개라 GitHub 로그인 필요) → 서버 · 앱 폴더에서 각각 설치

   ```bash
   git clone https://github.com/JTW16/IdeaApp.git
   cd IdeaApp/idea-helper/server && npm install
   cd ../app && npm install
   ```

3. `idea-helper/server/.env` 만들기 — `.env.example`을 복사하고 `GEMINI_API_KEY`, `DATABASE_URL`(Supabase Session pooler 주소 + 비밀번호), `JWT_SECRET`(긴 임의 문자열)을 채웁니다.
   **`DATABASE_URL`을 빠뜨리면 빈 DB로 시작합니다.** 키 · 비밀번호를 넘기는 방법은 바로 아래 'API 키 · DB 주소 넘기기'.
4. 아래 '당일 순서'대로 한 번 켜 보고 리허설합니다.

#### API 키 · DB 주소 넘기기 (팀원 노트북으로 발표할 때)

같이 발표하는 팀원과는 공유해도 됩니다. 다만 두 값이 무엇을 열어 주는지 알고 넘깁니다.

| 값 | 가진 사람이 할 수 있는 것 | 위험 |
|---|---|---|
| `GEMINI_API_KEY` | 지태웅 결제 계정으로 Gemini 사용 | 크레딧을 씀. 선불 크레딧 · 자동 충전 꺼짐이라 **최악이어도 남은 크레딧까지만** |
| `DATABASE_URL` (DB 비밀번호 포함) | Supabase DB를 **전부 읽고 · 고치고 · 지울 수 있음** | `npm run demo` 한 번이면 시연 데이터가 다 지워짐 |

1. **넘기는 방법** — 만나서 USB로 `.env` 파일을 옮기거나 직접 입력하는 게 가장 좋습니다(채팅 기록이 안 남음).
   메신저로 보내야 하면 **1:1 채팅**으로 보내고, 팀원이 `.env`에 넣은 뒤 **양쪽에서 메시지를 지웁니다.**
   - 넘길 값: `GEMINI_API_KEY`, `DATABASE_URL` 두 개. `JWT_SECRET`은 팀원이 아무 긴 문자열이나 넣어도 됨
   - 하지 말 것: Git에 올리기(`.env`는 `.gitignore`에 있음), 단체방 · 노션 · 스크린샷에 붙이기
2. **팀원에게 꼭 알려 줄 것**
   - **`npm run demo`는 Supabase 데이터를 전부 지운다** → 실행하기 전에 서로 말하고, 둘 중 한 명만
   - `.env` 파일을 다른 곳에 올리지 않기
3. **전날 팀원 노트북에서 리허설** — 서버 로그의 `DB: 외부 PostgreSQL (….pooler.supabase.com)`, `npm run check` 모두 ✅, Chrome에서 처음부터 끝까지 한 번.
   두 노트북이 같은 Supabase에 동시에 붙어도 괜찮으므로, 개발 PC는 **예비용**으로 켜 둘 수 있습니다.
4. **발표가 끝나면 바꾸기** — AI Studio에서 Gemini 키를 지우고 새로 발급, Supabase Database 설정에서 DB 비밀번호 재설정.
   새 값은 개발 PC의 `.env`에만 넣습니다(팀원 노트북의 옛 값은 더는 쓸 수 없게 됨).

리허설 · 시연에 쓰는 Gemini는 합쳐서 ₩100~200 정도입니다.

### 시연 전날

0. **Supabase 프로젝트 상태 확인** — 대시보드에서 프로젝트가 'Paused'(일시 정지)가 아닌지 봅니다. 무료 프로젝트는 한동안 안 쓰면 멈추고, 다시 켜는 데 몇 분 걸립니다.
1. (선택) 시연용 데이터를 처음 상태로 다시 채우기 — 서버를 끈 상태에서 실행. **Supabase의 아이디어 · 피드 · 나만의 카테고리 · 사용자를 지우고** 실제 AI로 피드 글 7~8개와 카테고리 3개(캠핑 요리 · 여행 앱 · 카페 창업)를 새로 넣습니다. 단어와 벡터는 그대로. AI를 약 11~14회 사용. **두 노트북이 같은 DB를 쓰므로 서로 말하고 한 명만** 실행

   ```bash
   cd idea-helper/server
   npm run demo
   ```

2. 아래 '시연 순서'대로 리허설합니다. Gemini 무료 한도라면 **리허설은 전날까지** 끝내고 당일엔 AI를 아낍니다.

### 시연 당일 (발표 30분 전)

1. 터미널 1 — 서버:

   ```bash
   cd IdeaApp/idea-helper/server && npm run dev
   ```

   로그에 `DB: 외부 PostgreSQL (….pooler.supabase.com)`이 나오면 정상
2. 터미널 2 — 앱:

   ```bash
   cd IdeaApp/idea-helper/app && npm run web
   ```

3. 터미널 3 — 점검 (AI를 1회 사용). 모두 ✅인지 확인:

   ```bash
   cd IdeaApp/idea-helper/server && npm run check
   ```

4. Chrome **시크릿 창**으로 http://localhost:8081 을 엽니다. (예전 기록 · 토큰이 남아 있지 않게)
5. 개발자 도구(F12)는 필요 없습니다. 창이 넓으면 앱이 가운데에 **휴대폰 크기(390×844) 틀**로 나옵니다 (창 높이가 낮으면 틀 높이만 줄어듦). 프로젝터에서 작으면 Ctrl + `+`로 배율을 125~150%로 올립니다.
   - 창 너비가 600px보다 좁으면(휴대폰 · 개발자 도구 모바일 모드) 틀 없이 화면을 꽉 채웁니다.

#### 당일 주의

- **터미널 1 · 2는 발표가 끝날 때까지 닫지 않습니다.** 닫으면 서버가 꺼집니다. 노트북 절전 · 화면 잠금도 꺼 둡니다.
- **Claude 앱의 미리보기로 켜지 않습니다.** 그렇게 켠 서버는 한동안 안 쓰면 자동으로 꺼집니다. 직접 터미널에서 켭니다.
- 처음 켤 때 **Windows 방화벽 창**이 뜨면 '허용' (같은 노트북 안에서만 쓰니 '개인 네트워크'면 충분).
- **인터넷이 끊기면 DB와 AI가 모두 멈춥니다.** 발표장 와이파이가 불안하면 휴대폰 핫스팟을 준비합니다.
- 비상 대책은 **백업 시연 영상**입니다. (내장 DB로 돌리는 방법은 데이터가 있는 개발 PC에서만 의미가 있음 — 아래 표 참고)

### 시연 순서 (약 5분)

| # | 할 일 | 보여줄 점 |
|---|---|---|
| 1 | 01에서 **음식 개발** | 기본 카테고리 + 다른 사용자가 만든 카테고리 |
| 2 | 단어 하나 📌 고정 → **다시 뽑기** | 고정한 단어는 남고 나머지만 바뀜 (리롤 0.5초 목표) |
| 3 | 방향성에 `여름 디저트` 입력 → Enter | 방향에 맞는 단어로 다시 뽑힘 (예: 아이스크림 · 빙수 · 수박) |
| 4 | **창조** | 03 → 04, 약 2~3초 (AI 5초 목표) |
| 5 | 04에서 **다시 뽑기**(또는 ‹) → 단어 그대로 → 다시 **창조** | 바로 결과 + "저장된 조합이라 AI를 부르지 않고 바로 보여드렸어요" (목표 4: 같은 조합 AI 호출 0회). 새 탭에서 http://localhost:4000/health 를 열면 `stats`에 AI로 만든 수 / DB에서 꺼낸 수가 보임 |
| 5-1 | 04에서 **다시 조합하기** (1~2번) | 같은 단어 3개로 다른 아이디어가 맨 위에 생기고, 이전 것은 아래로 내려감(스크롤). 카드를 눌러 확정할 것을 고름 (누를 때마다 AI 1회, 약 3초) |
| 6 | **확정** → **저장** → **진짜 만드는 법** | 저장 토스트, 재료 · 순서 (약 3~7초) |
| 7 | **공유하기** → **링크 복사** → 새 탭에 붙여넣기 | 앱 없이 보는 읽기 전용 웹 페이지 |
| 8 | 다시 **공유** → **피드에 올리기** | 피드 탭으로 이동: '내 아이디어' 표시, 다른 글에 👍, 인기순 정렬 |
| 9 | 하단 **🏠 홈** 탭 → 만들던 화면 그대로 → 상단 **홈** | 탭을 오가도 흐름이 유지되고, '홈'으로 01에 돌아감 |
| 10 | **+ 나만의 카테고리 추가** → `ㅁㄴㅇㄹ` 입력 | "어떤 분야인지 알기 어려운 이름이에요" (뜻 없는 이름 거절) |
| 11 | 이름을 `보드게임 카페`로 → **추가하고 시작** | DB에서 연관 단어를 찾아 새 카테고리로 바로 뽑기 |
| 12 | 하단 **🗒️ 기록** 탭 | 기기에 저장한 아이디어, 누르면 05로 다시 열림 |

방향성 예시로 잘 나오는 문장: `여름 디저트`, `매콤한 요리`, `아침 식사`, `튀김 요리`

### 문제가 생기면

| 증상 | 대처 |
|---|---|
| "AI가 답을 주지 못했습니다" | **다시 시도**. 서버가 이미 예비 모델 · 재시도를 거친 뒤라 잠깐 붐비는 상황입니다 |
| "AI 사용 한도를 다 썼어요" | 오늘 한도 초과. 피드 · 기록 · 공유 링크 · 같은 조합 재사용 위주로 진행 |
| "서버에 연결할 수 없습니다" | 터미널 1을 확인하고 `npm run dev` 다시 실행 |
| 데이터를 처음 상태로 | 서버를 끄고 `npm run demo` → 서버 다시 켜기 → 시크릿 창 새로 열기 |
| Supabase에 연결이 안 됨 (서버가 켜지다 멈춤, `DB 연결` 오류) | 인터넷 확인 → 대시보드에서 프로젝트가 멈췄는지 확인(Restore). **개발 PC에서만**: `server/.env`의 `DATABASE_URL` 줄 앞에 `#`을 붙이고 서버를 다시 켜면 내장 DB로 동작(10-19 옮기기 전 데이터). 다른 노트북에는 내장 DB 데이터가 없으므로 백업 영상으로 |
| 서버 · 앱 터미널을 실수로 닫음 | 같은 명령으로 다시 켜기 (데이터는 Supabase에 있어 그대로) |

서버 로그(터미널 1)에 `AI_QUOTA` · `AI_FAILED` · `AI_TIMEOUT` 줄이 찍히면 실제 원인이 함께 나옵니다.

## 2. 남은 일과 계획

목표: **발표 때 PC 브라우저(모바일 화면 크기)로 실제로 돌아가는 시연.** 스토어 배포는 범위 밖.

우선순위: 🔴 시연 전 필수 · 🟠 고치면 좋은 버그 · 🟡 추가하면 좋은 것 · ⚪ 실제 배포 때 (지금은 안 함)

### 지금 상태 (이어서 시작할 때)

```bash
cd idea-helper/server && npm run dev      # 서버 (4000)
cd idea-helper/app && npm run web         # 앱 (8081)
cd idea-helper/server && npm run check    # 점검 (Gemini 1회 사용)
```

- 서버 테스트 18개(기존 7 + 추가 11) · 서버/앱 타입 검사 · 앱 lint 통과
- PC 브라우저로 전 화면 확인 완료 (10-16): 카테고리 → 단어(고정 · 방향성 · 다시 뽑기) → 창조 → 결과 → 확정 → 저장 → 만드는 법 → 링크 복사 → 피드(반응 · 정렬) → 기록 → 나만의 카테고리
- 하단 탭 바 · 뒤로 · 홈 버튼 확인 완료 (10-17): 탭 전환, 탭을 오가도 만들던 화면 유지, 홈 탭 다시 누르면 01, 상단 '홈' → 01, 기록 → 05 → 뒤로 → 01, 공유 → 피드에 올리기 → 피드 탭(방금 올린 글 보임), 기록 삭제
- DB는 **Supabase**(10-19부터, `server/.env`의 `DATABASE_URL`). 내장 PGlite(`server/.data/pglite`)는 비상용으로 남김. 시연 데이터(10-19 `npm run demo`: 피드 글 8개, 나만의 카테고리 3개). 백업: `pglite-backup-20261016`, `pglite-backup-20261018`(단어 늘리기 직전)

## 3. 기획서 대비 검토와 평가

> 비교한 문서: 기획서(4주차) · 3주차 요구사항 · 화면 상세 명세(5주차) · 아키텍처 통합본(6주차)
> 비교한 앱: 2026-10-19 `main` (다시 조합하기 · 휴대폰 크기 틀까지 반영)

### 결론

**기획서의 핵심 목표는 모두 달성했다.** Must 6개와 목표 숫자 4개를 다 채웠고, Should도 대부분 구현해 기획서보다 기능이 많다.

부족한 것은 세 가지다.
1. **신고 기능 없음** (기획서 위험 대응 항목)
2. **실기기 측정이 아님** (PC 브라우저에서 잰 숫자)
3. **HTTPS 배포 없음** (로컬 시연으로 범위를 줄였기 때문)

---

### 1. ✅ 기획서대로 잘 된 것

#### 목표 숫자 4개 (기획서 2번)

| 목표 | 결과 | 평가 |
|---|---|---|
| 1. 단어 다시 뽑기 0.5초 이내 | 평균 27ms · 최대 30ms (Supabase 경유) | 목표보다 약 18배 빠름 |
| 2. AI 결과 5초 이내 | 1.9~3.4초 (10-16 · 10-19 측정 전부) | 달성 |
| 3. 카테고리당 단어 100개 이상 | 265~309개 (서버 테스트로 확인) | 약 3배 |
| 4. 같은 조합이면 AI 호출 0회 | 서버 테스트 · `/health` 통계 · 앱 문구("저장된 조합이라 AI를 부르지 않고…")로 확인 | 달성. 단어 순서가 달라도 같은 조합으로 봄 |

#### Must 6개

카테고리 선택 → 랜덤 단어 3개 → 다시 뽑기 → 창조 → 반복 → 조합 결과 DB 저장 · 재사용. 모두 동작한다.

#### 기획서 3번 '해결 방향과 선택'

| 선택 | 구현 |
|---|---|
| DB를 먼저 보고, 없을 때만 AI 호출 | `POST /ideas` — 조합 키로 조회 후 없을 때만 Gemini |
| 로그인 없음 | 기기 ID → 서버가 익명 토큰(JWT) 발급 |
| 단어는 카테고리별 DB | PostgreSQL(Supabase) `words` · `category_words` |
| 조합 키 = 카테고리 + 단어 3개 | 카테고리 + 정렬한 단어 3개 + 방향성 (`ideas.combo_key UNIQUE`) |

#### 보안 (기획서 위험 2)

- API 키는 서버 `.env`에만 있음. 앱 코드 · Git에 없음
- 기기별 AI 호출 제한 (분당 12회)
- 금칙어 검사: 사용자 입력과 AI 결과 모두

#### 화면 상세 명세

화면 9개, 각 화면의 빈 · 로딩 · 오류 상태, 버튼별 이동 표를 거의 그대로 구현했다. 예:

- 01-1 나만의 카테고리: 이름 2~20자, 연관 단어 10개 미만이면 추가 불가, 이미 있는 이름이면 그 카테고리로 시작
- 02 단어 화면: 고정 최대 2개, 고정한 단어는 다시 뽑기에서 빠짐, 방향성에 맞는 단어가 부족하면 안내
- 03 결과 준비: '취소'하면 고정 유지하고 02로, 서버의 AI 호출도 멈춤
- 06 공유 시트: 바깥을 눌러도 닫힘, 링크 복사 토스트
- 07 피드: 내용 2줄 · 누르면 펼침, 반응은 하나만(다시 누르면 취소, 내 글엔 불가), '내 아이디어' 표시

#### 위험 대응이 실제로 만들어진 것

- 위험 1 (AI 5초 초과): 5초 시간 제한, 붐비면 예비 모델로, 실패하면 '다시 시도' 안내
- 위험 4 (같은 조합은 늘 같은 결과): '새로 생성'을 **'다시 조합하기'**로 구현

#### 테스트

서버 테스트 18개(핵심 흐름 7 + 고친 부분 11). 실제 Gemini · Supabase 없이 돌아간다.

### 5. ⚠️ 알아둘 점

#### 이미지 프롬프트 제안이 기획서와 부딪힘

- 기획서는 'AI 이미지 생성'을 **Won't(이번 학기에 안 함)**로 정했고, '사진: 사용하지 않음(텍스트 기반)'이라고 했다.
- 화면 상세 04 결과 화면의 '절대 넣지 않는 것'에도 '이미지 생성'이 있다.
- 다만 [4. 제안](#4-제안-이미지-프롬프트-복사-버튼)는 앱이 그림을 만드는 게 아니라 **프롬프트만 복사**한다. "기획서 원칙(앱은 텍스트만)은 지키면서, 그림은 사용자 몫"으로 설명할 수 있다.
- → 팀 상의 때 이 점을 같이 이야기할 것.

#### 남은 버그 · 미흡한 부분 (자세히는 [2. 남은 일과 계획](#2-남은-일과-계획) 🟠)

- 카테고리 사용 횟수가 '창조'마다 오름(DB에서 꺼낸 결과 포함) → '많이 쓴 순'이 부풀 수 있음. **팀이 의미를 정해야 함**
- 피드 '인기순'이 좋아요 수만 봄
- 기록 삭제가 확인 없이 바로 지워짐
- 셋 다 시연에는 지장 없음

#### Gemini 모델 이름

10-19에 가격을 확인할 때 `gemini-3.5-flash`는 지원이 끝나 새 모델로 자동 연결된다는 정보가 있었다. 지금은 정상 동작하지만 **발표 전에 `server/.env`의 `GEMINI_MODEL`을 한 번 확인**하는 게 안전하다.

## 4. 제안: 이미지 프롬프트 복사 버튼

> 상태: **아이디어 단계 — 아직 만들지 않음.** 팀원과 상의 후 정한다.
> 정해진 것(지태웅): 아래 '정한 것' 4가지. 팀 상의가 필요한 것은 맨 아래 '팀이 정할 것'.

### 한 줄 요약

04 결과 화면의 아이디어 카드마다 오른쪽 위에 버튼을 두고, 누르면 **그 아이디어를 그림으로 그려 달라는 영어 프롬프트**가 복사된다.
사용자는 이 글을 ChatGPT · Gemini · Midjourney 등 **아무 이미지 생성 AI에 붙여 넣어** 아이디어를 그림으로 본다.

### 왜

- '캠핑용 크레페 덮밥 키트'처럼 글로만 보면 "이게 뭐지?" 싶은 결과가 있다. 그림으로 한 번 보면 훨씬 잘 와닿는다.
- 앱이 직접 그림을 만들면 비용 · 시간(이미지 생성은 수 초~수십 초)이 든다. 앱은 **좋은 프롬프트만 만들어 주고**, 그리는 것은 사용자가 쓰는 AI에 맡긴다.
- 추후 확장: 나중에 앱 안에서 바로 이미지를 만드는 기능으로 넓힐 수 있는 첫 단계.

### 정한 것

| # | 항목 | 결정 |
|---|---|---|
| 1 | 버튼 위치 | **결과 카드마다 하나씩** (조합 1 · 2 · 3 … 각각). 글만 보고 "실제 이미지로 보고 싶다"는 사람이 쓰는 기능이라 고른 카드에만 둘 이유가 없음 |
| 2 | 프롬프트 만드는 방법 | **(가) 정해진 틀에 제목 · 설명 · 단어를 끼워 넣기** — 바로 되고 AI 비용 0. (나) Gemini에게 프롬프트를 쓰게 하는 방법은 나중에 |
| 3 | 프롬프트 언어 | **영어** |
| 4 | 분야별 그림 스타일 | **일단 통일** (음식 · 프로그램 · 공모전 모두 같은 틀). 분야별로 다르게 할지는 추후 결정 |

### 화면

```
┌─────────────────────────────────┐
│ 조합 1 · ✓ 고름            [🎨] │  ← 카드 오른쪽 위 작은 버튼 (이미지 프롬프트 복사)
│                                 │
│ 캠핑용 크레페 덮밥 키트         │
│ 야외에서 간편하게 팬 하나로 …   │
└─────────────────────────────────┘
```

- 누르면 클립보드에 복사 + 토스트 **"이미지 프롬프트를 복사했어요. 이미지 AI에 붙여 넣어 보세요"**
- 결과가 1개일 때(조합 번호가 없을 때)도 같은 자리에 버튼
- 버튼 모양(🎨 아이콘만 / '이미지' 글자 포함)은 팀이 정할 것

### 프롬프트 틀 (영어, 분야 공통)


#### 알아둘 점 (방식 (가)의 한계)

- **지시문은 영어지만 제목 · 설명 · 단어는 한국어 그대로** 들어간다. (가)는 AI를 쓰지 않아서 번역을 못 함.
  - ChatGPT · Gemini는 한국어가 섞여도 잘 이해함. Midjourney 같은 일부 이미지 AI는 한국어를 잘 못 알아들을 수 있음.
  - 전부 영어로 만들려면 (나) 방식(Gemini가 번역 + 프롬프트 작성, 누를 때마다 AI 1회 · 1~2초)이 필요.
- 영어로 하는 이유 '토큰이 싸다'에 대해: 이 프롬프트는 **사용자가 자기 AI에 붙여 넣는 것**이라 우리 Gemini 비용과는 관계없음. 영어의 실제 장점은 이미지 AI가 영어 지시를 더 정확히 따른다는 점.
- 'product-photo style' 한 줄이 음식에는 잘 맞지만 프로그램 개발(앱 화면) · 공모전(행사 · 서비스)에는 어색할 수 있음 → 4번 '분야별 스타일'을 정할 때 같이 보기.

### 만든다면 (구현 메모)

- 앱만 바꾸면 됨 (서버 · DB 변경 없음, AI 호출 0회)
  - `app/src/lib/imagePrompt.ts` (신규): `buildImagePrompt(idea: Idea): string` — 위 틀에 값 넣기
  - `app/src/app/(tabs)/(home)/result.tsx`: 카드마다 버튼, `expo-clipboard`의 `Clipboard.setStringAsync` (06 '링크 복사'와 같은 방식) + `showToast`
- ⚠ 결과가 2개 이상이면 카드 전체가 '고르기' 버튼(Pressable)이라, 그 안에 버튼을 넣으면 웹에서 `<button>` 안 `<button>` 오류가 난다.
  기록 탭의 '삭제'처럼 **카드 위에 겹쳐 놓은 형제 요소**로 둔다 (`(tabs)/saved.tsx` 참고).

- 예상 작업량: 반나절 이하 (화면 1개 + 작은 함수 1개)

## 5. API 명세: 분야별 후속 가이드

> 상태: **명세만 작성 (2026-10-28), 아직 만들지 않음.** 교수님 버전 API 목록의 `POST /app/ideas/{id}/guide`를 참고했다.
> 지금의 `POST /ideas/:id/recipe`(만드는 법)를 대신하는 새 API다. 예전 경로는 그대로 남긴다(하위 호환).

### 5-1. 왜 바꾸나

- 지금 만드는 법은 **2종류**뿐이다: 음식이면 '재료 · 만드는 순서', 그 밖에는 모두 '준비물 · 실행 단계'.
- 그래서 **공모전 주제선정** 아이디어에도 '준비물 · 실행 단계'가 나온다. 공모전 아이디어에 필요한 것은 **기획안**(배경 · 목표 · 대상 · 실행 계획 · 기대 효과)이다.
- 프로그램 개발도 '준비물'보다 **핵심 기능 · 기술 · 구현 순서**가 맞다.
- 분야마다 항목이 달라지므로, 응답을 '재료 / 순서' 고정 칸이 아니라 **제목이 붙은 절(section) 목록**으로 바꾼다.

### 5-2. 한눈에 보기

| 항목 | 내용 |
|---|---|
| 요청 | `POST /ideas/{id}/guide` |
| 인증 | 필요 (`Authorization: Bearer <익명 토큰>`) |
| 요청 본문 | 없음 (`{}`) |
| 하는 일 | 아이디어의 카테고리를 보고 가이드 종류를 정해, 저장된 가이드가 있으면 그대로, 없으면 Gemini로 만들어 저장 |
| AI 호출 | 처음 한 번만 (아이디어당 가이드 1개, 이후 DB에서) |
| 시간 제한 | 20초 (`LLM_RECIPE_TIMEOUT_MS`, 만드는 법과 같은 값) |
| 호출 제한 | AI 공통 제한 (사용자당 분당 12회) |
| 화면 | 05 아이디어 확정 → 05-1 (화면 제목이 종류에 따라 바뀜) |

### 5-3. 가이드 종류 4가지

카테고리 이름으로 정한다. **위에서부터 차례로** 검사하고, 처음 맞는 것을 쓴다.

| 순서 | 종류 (`kind`) | 화면 제목 | 정하는 기준 (카테고리 이름에 들어 있으면) | 예 |
|---|---|---|---|---|
| 1 | `recipe` | 만드는 법 | 지금의 음식 판별 그대로 (음식 · 요리 · 레시피 · 메뉴 · 디저트 · 베이킹 · 음료 · 간식 · 반찬 · 빵 · 과자 · 안주 · 주류 · 칵테일 · 도시락 · 밀키트) | 음식 개발, 캠핑 요리 |
| 2 | `proposal` | 공모전 기획안 | 공모전 · 대회 · 경진 · 캠페인 · 축제 · 행사 · 정책 · 주제 | 공모전 주제선정 |
| 3 | `build` | 구현 가이드 | 프로그램 · 앱 · 어플 · 웹 · 사이트 · 서비스 · 개발 · 코딩 · 게임 · 소프트웨어 · 챗봇 | 프로그램 개발, 여행 앱 |
| 4 | `plan` | 실행 계획 | 위 어디에도 안 맞으면 (지금의 '준비물 · 실행 단계'와 같음) | 카페 창업 |

- '음식 개발'은 '개발'이 들어 있지만 1번에서 먼저 걸리므로 `recipe`다. 그래서 순서가 중요하다.
- 기본 카테고리 3개는 항상 정해진 종류: 음식 개발 = `recipe`, 프로그램 개발 = `build`, 공모전 주제선정 = `proposal`.
- 함정: 지금 음식 판별에서 '술' · '카페'를 뺀 이유(기'술' 창업 · 미'술' 수업 · 카페 '창업'이 음식으로 판별됨)가 그대로 적용된다. 새 낱말을 추가할 때도 다른 낱말 안에 들어가는 짧은 글자는 피한다. (예: '웹'은 '웹툰'에도 들어감 → 웹툰 창작이 `build`가 되는지 정할 때 확인)

### 5-4. 종류별 내용

요약 3칸과 절(section) 목록. 절의 표시 방식: `bullet` = 점 목록, `numbered` = 번호 목록, `text` = 문단.

| 종류 | 요약 3칸 | 절 (순서대로) |
|---|---|---|
| `recipe` 만드는 법 | 조리 시간 · 난이도 · 분량 | 재료 (`bullet`, 4~8개, 분량 포함) → 만드는 순서 (`numbered`, 4~6단계) |
| `build` 구현 가이드 | 개발 기간 · 난이도 · 필요 인원 | 핵심 기능 (`bullet`, 3~5개) → 기술 · 준비물 (`bullet`, 3~6개) → 구현 순서 (`numbered`, 4~6단계) |
| `proposal` 공모전 기획안 | 준비 기간 · 난이도 · 팀 규모 | 배경 · 문제 (`text`, 1~2문장) → 목표 (`bullet`, 2~3개) → 대상 (`text`, 1문장) → 실행 계획 (`numbered`, 4~6단계) → 기대 효과 (`bullet`, 2~3개) |
| `plan` 실행 계획 | 기간 · 난이도 · 인원 · 규모 | 준비물 (`bullet`, 4~8개) → 실행 단계 (`numbered`, 4~6단계) |

- **절 제목 · 요약 칸 이름은 서버가 정한다.** AI에게는 칸 순서대로 값만 받는다(이름을 AI가 지어내면 화면마다 달라짐).
- 난이도는 `쉬움 · 보통 · 어려움` 중 하나.
- 현실적으로 만들 수 없는 아이디어면 `feasible: false`, 요약 · 절은 비운다(지금과 같음).

### 5-5. 응답

**200 OK**

```json
{
  "guide": {
    "ideaId": 212,
    "kind": "proposal",
    "title": "공모전 기획안",
    "feasible": true,
    "summary": [
      { "label": "준비 기간", "value": "6주" },
      { "label": "난이도", "value": "보통" },
      { "label": "팀 규모", "value": "3~4명" }
    ],
    "sections": [
      { "heading": "배경 · 문제", "style": "text", "items": ["전통시장 상인 대부분이 고령이라 키오스크 · 간편결제 도입이 늦다."] },
      { "heading": "목표", "style": "bullet", "items": ["노인 상인도 3분 안에 쓰는 음성 주문", "시장 매출 데이터 확보"] },
      { "heading": "대상", "style": "text", "items": ["지역 전통시장 상인과 방문객"] },
      { "heading": "실행 계획", "style": "numbered", "items": ["상인 인터뷰 10명", "음성 주문 시나리오 설계", "시제품 제작", "시장 1곳 시범 운영"] },
      { "heading": "기대 효과", "style": "bullet", "items": ["주문 대기 시간 단축", "디지털 소외 완화"] }
    ]
  },
  "fromCache": false
}
```

| 필드 | 형식 | 설명 |
|---|---|---|
| `guide.ideaId` | number | 아이디어 번호 |
| `guide.kind` | `recipe` · `build` · `proposal` · `plan` 중 하나 | 가이드 종류 (5-3) |
| `guide.title` | string | 05-1 화면 제목 ("만드는 법" · "구현 가이드" · "공모전 기획안" · "실행 계획") |
| `guide.feasible` | boolean | false면 "만들기 어려운 아이디어예요" 화면 |
| `guide.summary` | `{ label, value }` 3개 | 위쪽 칩 3개 |
| `guide.sections` | `{ heading, style, items }` 목록 | 절 목록. `items`는 글 목록(절마다 최대 10개) |
| `fromCache` | boolean | true면 저장된 가이드를 꺼낸 것 (AI 0회) |

**오류** (지금 API들과 같은 형식: `{ "error": { "code", "message" } }`)

| 상태 | `code` | 언제 |
|---|---|---|
| 400 | `BAD_REQUEST` | 아이디어 번호가 숫자가 아님 |
| 401 | `UNAUTHORIZED` | 토큰이 없거나 만료 (앱이 자동 재발급) |
| 404 | `IDEA_NOT_FOUND` | 없는 아이디어이거나 숨김 처리된 아이디어 |
| 429 | `RATE_LIMITED` / `AI_QUOTA` | 분당 호출 제한 / Gemini 한도 · 크레딧 소진 |
| 502 | `AI_FAILED` · `AI_BAD_OUTPUT` | AI 오류 · 형식이 깨진 답 (저장하지 않음) |
| 504 | `AI_TIMEOUT` | 20초 초과 |

### 5-6. 서버 처리 순서

1. 토큰 확인 → 아이디어 불러오기 (없거나 숨김이면 404)
2. `guides` 테이블에 그 아이디어의 가이드가 있으면 그대로 돌려준다 (`fromCache: true`, AI 0회)
3. **예전 만드는 법 이어 쓰기:** 가이드는 없지만 `recipes`에 예전 만드는 법이 있고, 새 종류가 `recipe`나 `plan`이면 그 내용을 절 형식으로 바꿔 `guides`에 저장하고 돌려준다 (AI 0회). `build` · `proposal`이면 예전 것은 두고 새로 만든다
4. 호출 제한 확인 → 카테고리로 종류 결정 → 종류별 프롬프트로 Gemini 호출 (JSON 형식 강제, 20초 제한, 결과가 깨지면 한 번 더 시도: 지금과 같음)
5. 빈 값 · 금칙어 검사 → `guides`에 저장 (동시에 두 번 와도 `ON CONFLICT DO NOTHING`으로 한 건만) → 돌려준다

**프롬프트 (종류별로 바뀌는 부분만):** "카테고리 · 아이디어 제목 · 설명 · 사용한 단어"는 지금과 같다. 그 아래에 종류별로
"`summary`에는 [조리 시간, 난이도, 분량]을 순서대로, `sections`에는 [재료 4~8개, 만드는 순서 4~6단계]를 순서대로 쓴다"처럼
칸 이름과 개수를 알려 주고, 응답 형식은 `{ feasible: boolean, summary: string[3], sections: string[][] }`로 강제한다. 서버가 여기에 칸 이름 · 절 제목 · 표시 방식을 붙인다.

### 5-7. DB

새 테이블 하나. `schema.sql`에 `CREATE TABLE IF NOT EXISTS`로 추가하면 서버를 켤 때 자동으로 만들어진다(Supabase 포함). 기존 `recipes`는 지우지 않는다.

```sql
-- 후속 가이드: 조합 결과와 1:1, 한 번 만들면 재사용 (recipes를 대신함, recipes는 예전 앱 · 예전 데이터용으로 남김)
CREATE TABLE IF NOT EXISTS guides (
  idea_id int PRIMARY KEY REFERENCES ideas(id) ON DELETE CASCADE,
  kind text NOT NULL CHECK (kind IN ('recipe', 'build', 'proposal', 'plan')),
  feasible boolean NOT NULL,
  summary jsonb NOT NULL,   -- [{label, value}] 3개
  sections jsonb NOT NULL,  -- [{heading, style, items}]
  created_at timestamptz NOT NULL DEFAULT now()
);
```

- `db.ts`의 DB 옮기기 목록(`TABLES`)에 `guides`를 `recipes` 다음에 추가한다.
- 숨긴 아이디어를 새로 만들 때(`POST /ideas`) 지우는 대상에 `guides`도 추가한다(지금은 `recipes` · `posts`만 지움).
- `npm run demo`의 초기화(`DELETE FROM recipes`)에도 `guides`를 추가한다.

### 5-9. 확인할 것 (테스트)

예시 AI로 (Gemini 비용 0):

1. 종류 판별: 음식 개발 → `recipe`, 공모전 주제선정 → `proposal`, 프로그램 개발 · 여행 앱 → `build`, 카페 창업 → `plan`, 기술 창업 → `plan`('술' 함정이 다시 생기지 않는지)
2. 처음 요청은 AI 1회 + 저장, 두 번째는 `fromCache: true` · AI 0회
3. 종류별로 절 제목 · 개수가 5-4 표와 같다
4. 예전 `recipes`가 있는 음식 아이디어 → AI 0회로 가이드가 나온다 / 공모전 아이디어 → 새로 만든다
5. 숨긴 아이디어 → 404, 없는 번호 → 404
6. 예전 경로 `POST /ideas/:id/recipe`가 그대로 동작한다

실제 Gemini로 (발표 전 한 번): 세 기본 카테고리에서 하나씩 만들어 20초 안에 나오는지, 기획안이 공모전답게 나오는지 확인. **Gemini 약 3~6회 (₩200 이하).**

### 5-10. 정할 것

1. 종류 이름 · 화면 제목 (위 4가지로 갈지)
2. 공모전 기획안의 절 구성 (배경 · 목표 · 대상 · 실행 계획 · 기대 효과로 충분한지)
3. 나만의 카테고리 판별을 낱말 기준(5-3)으로 할지, 이름 벡터와 가장 가까운 기본 카테고리를 따라가게 할지 (후자는 더 정확하지만 임베딩이 필요해 조금 복잡)
4. 예전 경로 `/recipe`를 앱에서 언제 완전히 뺄지
