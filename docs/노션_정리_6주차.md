## 6주차 — 기술 선택, 구성도, 데이터 · API 목록과 결정 기록

**무엇을 했나**: 4주차 기획서와 5주차 화면 명세를 바탕으로 시스템 아키텍처를 설계했습니다. 기술을 고르고, 구성도(상자 7개 · 화살표 7개)를 그린 뒤, 데이터와 API 목록을 뽑고, 아키텍처에 가장 크게 영향을 주는 결정 두 개를 기록했습니다.

**한 줄 요약**: React Native 앱 → Node.js API 서버(익명 토큰 발급 · 조합 조회) → PostgreSQL + pgvector → 같은 조합이 DB에 없을 때만 Gemini 호출. 사진과 로그인은 쓰지 않습니다.

**기술 선택**

| 선택 지점 | 우리 팀의 선택 | 이유 | 버린 선택지 |
|---|---|---|---|
| 클라이언트 | React Native (Expo) + TypeScript, Android 우선, 기기 저장은 SQLite | 모바일 앱으로 정했고 성능을 실기기로 잼. 한 코드로 Android · iOS. 서버와 같은 TypeScript라 언어가 하나 | Flutter, Kotlin · Swift 따로 개발, 웹 앱(PWA) |
| 서버 | Node.js (TypeScript) + Fastify, 클라우드(PaaS)에 배포 | LLM API 키를 서버 환경변수에만 둠. "DB에 있으면 꺼내고 없으면 AI 호출"을 서버 한 곳에서 처리. 상시 실행이라 콜드 스타트 · 실행 시간 제한이 없음 | Supabase, Spring Boot, Firebase Cloud Functions, 앱에서 LLM 직접 호출(키 노출) |
| 데이터베이스 | PostgreSQL + pgvector (관리형) | 서로 연결된 관계형 데이터. "같은 조합 1개", "글마다 반응 1개"를 DB 제약으로 보장. 연관 단어 검색도 같은 DB에서 | Firestore, MongoDB, 앱 안 SQLite만 사용 |
| 사진 저장 | 사용하지 않음 (텍스트만) | 4주차 기획서 결정. 피드 · 공유 링크도 텍스트 카드로 충분 | 사진 저장소(S3 등), AI 이미지 생성 |
| 인증 | 로그인 없음. 첫 실행 때 서버가 기기마다 익명 ID와 토큰(JWT)을 발급 | "내 글" 표시, 글마다 반응 1개, 기기별 AI 호출 제한에 기기 구분이 필요. 서버가 서명한 토큰이라 조작에 강함 | 이메일 · 소셜 로그인, 아무 식별 없음 |
| 배포 위치 | 앱: Expo(EAS) 빌드 → Google Play 내부 테스트. 서버: PaaS(Render · Railway 등). DB: 관리형 PostgreSQL. 모두 HTTPS | 실기기 시연에 충분. 가까운 리전일수록 0.5초 · 5초 목표에 유리 | AWS EC2 직접 배포, 학교 서버, 정식 스토어 출시 |
| AI 호출 (팀이 추가) | Google Gemini API, Flash 계열 소형 모델. 같은 조합이 DB에 없을 때만 호출 | 5초 목표라 빠르고 저렴한 모델. 프롬프트를 "카테고리 + 세 단어 (+ 방향성)"으로 고정 | 매번 호출, 자체 AI 모델, 큰 모델 |
| 연관 단어 매칭 (팀이 추가, Should) | Gemini 임베딩으로 만든 벡터를 pgvector에 저장해 유사도 검색 | 나만의 카테고리 · 방향성은 미리 준비할 수 없음. 단어 벡터는 한 번만 계산 → 뽑을 때는 DB 쿼리만 (리롤 0.5초 유지) | 매번 LLM이 단어 고르기, 태그를 손으로 달기 |

**구성도**: 앱은 우리 API 서버하고만 통신하고, 외부 AI는 서버만 부릅니다. (그림은 아래 architecture.pdf 참고)

| 상자 | 무엇인가 | 기술 | 만드나 / 빌려 쓰나 |
|---|---|---|---|
| 모바일 앱 | 화면 9개, 저장한 아이디어를 기기에 보관 | React Native (Expo) + TypeScript, SQLite | 만든다 |
| API 서버 | 단어 뽑기, 조합 캐시 조회, AI 호출, 카테고리 매칭, 피드 · 반응, 익명 토큰, 호출 제한 | Node.js (TypeScript) + Fastify | 만든다 (실행 환경은 빌려 씀) |
| 익명 인증 | 기기마다 익명 ID · 토큰 발급 | 서버가 직접 발급하는 JWT | 만든다 (API 서버에 포함) |
| 데이터베이스 | 카테고리, 단어, 조합 결과, 만드는 법, 공유 글, 반응 등 | PostgreSQL + pgvector | 빌려 쓴다 (테이블 · 쿼리는 우리가) |
| 외부 LLM API | 세 단어 조합 아이디어, 만드는 법 생성 | Gemini API (Flash 계열) | 빌려 쓴다 (프롬프트는 우리가) |
| 임베딩 API (Should) | 단어 · 카테고리 이름 · 방향성을 벡터로 | Gemini API (임베딩 모델) | 빌려 쓴다 |
| 공유 링크 웹 페이지 (Should) | 앱이 없는 사람이 링크로 아이디어를 읽기 전용으로 봄 | API 서버가 HTML 반환 | 만든다 (API 서버에 포함) |

| 화살표 | 어디서 → 어디로 | 무엇을 주고받나 |
|---|---|---|
| ① | 모바일 앱 → 익명 인증 | 첫 실행 때 익명 로그인 요청 → 익명 ID · 토큰 |
| ② | 모바일 앱 → API 서버 | 요청 + 토큰 → JSON 응답 (모두 HTTPS) |
| ③ | API 서버 → 데이터베이스 | 랜덤 단어 추출, 연관 단어 검색, 조합 키로 캐시 조회 · 저장, 피드 · 반응 읽기/쓰기 |
| ④ | API 서버 → 외부 LLM API | DB에 같은 조합이 없을 때만 프롬프트 → 아이디어 또는 만드는 법 |
| ⑤ | API 서버 → 임베딩 API | 새 카테고리 이름 · 방향성 문장 → 벡터 (같은 문장은 저장해 두고 재사용) |
| ⑥ | 링크 받은 사람(브라우저) → 공유 링크 웹 페이지 | 링크 열기 → 읽기 전용 페이지 |
| ⑦ | 공유 링크 웹 페이지 → 데이터베이스 | 공유 코드로 글 조회 |

**데이터 목록**: 서버 DB에 9덩어리, 기기에 1덩어리를 둡니다. 핵심은 **조합 키**(카테고리 + 정렬한 단어 3개 + 방향성)로, 이 키가 같은 조합의 AI 호출 0회를 보장합니다.

| 덩어리 | 들어가는 정보 | 어느 화면 | 관계 |
|---|---|---|---|
| 카테고리 | 이름(2~20자, 중복 불가), 종류(기본 / 사용자 추가), 이름 벡터, 선택된 횟수 | 01, 01-1, 02 | 매칭을 통해 단어와 N : M |
| 단어 | 단어, 임베딩 벡터 | 02, 01-1 (기본 카테고리당 100개 이상 미리 입력) | 조합 결과 하나에 3개씩 쓰임 |
| 카테고리-단어 매칭 | 카테고리, 단어, 연관 점수 | 01-1, 02 | 나만의 카테고리는 매칭된 단어 10개 이상 |
| 조합 결과 (아이디어) | 단어 3개, 방향성, **조합 키(유일)**, 제목 · 내용, 신고 수, 숨김 여부 | 03, 04, 05 | 만드는 법 1 : 1, 공유 글 1 : N |
| 만드는 법 | 요약(시간 · 난이도 · 분량), 재료, 순서 4~6단계 | 05-1 | 한 번 만들면 재사용 |
| 공유 글 | 공개 범위(링크만 / 피드), 익명 닉네임, 공유 링크 코드, 반응 수 | 06, 07, 공유 웹 | 반응 1 : N |
| 반응 | 종류(좋아요 / 그저그래요 / 별로에요) | 07 | (글, 익명 ID)당 1개, 취소하면 삭제 |
| 익명 사용자 | 익명 ID, 닉네임(#번호) | 앱 첫 실행 | 이름 · 연락처는 받지 않음 |
| 신고 | 대상(아이디어 또는 글), 익명 ID | 화면 미설계 (위험 대응) | 일정 수 이상이면 숨김 |
| 기기에 저장한 아이디어 | 제목, 설명, 단어 3개, 만드는 법 | 05 '저장' | 서버에 올리지 않음 |

**API 목록**: 핵심 9개 중 처음 4개가 중간 발표(Must) 범위, 나머지는 최종 발표(Should) 범위입니다. 익명 로그인을 뺀 모든 요청은 토큰을 붙이고, 서버가 먼저 토큰을 확인합니다.

| 화면의 행동 | 요청 이름 | 서버가 확인할 것 | 돌려주는 것 |
|---|---|---|---|
| 앱 처음 실행 (Must) | POST /auth/anonymous | 기기 값 형식, 같은 기기면 기존 ID 재사용, 발급 횟수 제한 | 익명 ID, 닉네임, 토큰 |
| 01 화면 열기 (Must) | GET /categories | 토큰 | 기본 카테고리 + 다른 사용자가 만든 카테고리(많이 쓴 순) |
| 02 단어 뽑기 · 다시 뽑기 · 방향성 (Must) | POST /words/draw | 고정 단어 2개 이하 · 같은 카테고리, 방향성 50자 이하 · 맞는 단어 3개 이상 | 단어 3개 (목표 0.5초) |
| 02 → 03 '창조' (Must) | POST /ideas | 단어 3개가 서로 다르고 같은 카테고리, **조합 키로 DB 먼저 조회** → 없을 때만 LLM 호출(5초 제한), 실패한 결과는 저장 안 함 | 아이디어, DB에서 꺼냈는지 여부(목표 4번 확인용) |
| 05 → 05-1 만드는 법 | POST /ideas/{id}/recipe | 저장된 게 있으면 그대로, 없을 때만 LLM 생성 | 시간 · 난이도 · 분량, 재료, 순서 |
| 01-1 '추가하고 시작' | POST /categories | 2~20자 · 금칙어, 같은 이름이면 기존 ID, 연관 단어 10개 이상, 하루 추가 횟수 제한 | 카테고리 ID 또는 '이미 있음' · '단어 부족' |
| 06 '피드에 올리기' | POST /posts | 숨김 글 아닌지, 같은 아이디어 중복 게시 금지 | 글 ID, 공유 링크 코드, 닉네임 |
| 07 피드 열기 · 정렬 | GET /posts | 정렬 값, 한 번에 20개 이하, 숨김 글 제외 | 글 목록 + 다음 페이지 커서 |
| 07 반응 누르기 · 바꾸기 · 취소 | PUT /posts/{id}/reaction | 내 글이 아닌지, (글, 익명 ID)당 1개 | 바뀐 반응 수, 내 반응 |

**결정 기록 ① 서버를 직접 만든다 (Node.js)**

| 항목 | 내용 |
|---|---|
| 상황 | LLM API 키를 앱 밖에 숨겨야 하고, 같은 조합이면 DB에서 꺼내는 로직이 필요. 로그인은 없지만 기기 구분은 필요. 11주차 중간 발표까지 핵심 루프 완성 |
| 선택지 | ① Node.js 서버 + 관리형 PostgreSQL ② Spring Boot ③ Supabase ④ Firebase |
| 결정 | ① Node.js (TypeScript) 서버 + 관리형 PostgreSQL |
| 이유 | 앱과 같은 TypeScript라 언어가 하나이고 요청 · 응답 타입을 공유. 대기 시간 대부분이 AI · DB 응답이라 Node의 비동기 처리에 맞음. 상시 실행이라 콜드 스타트가 없음. 관계형 DB가 "같은 조합 1개", "반응 1개" 규칙을 보장 |
| 감수한 단점 | 익명 토큰 · 호출 제한 · 배포를 직접 만들고 운영해야 함. 무료 플랜은 절전 후 첫 응답이 느릴 수 있어 5초 목표를 9주차에 미리 측정. 앱을 재설치하면 이전 "내 글" 연결이 끊김 |
| 결정한 사람 (A) | 지태웅 |

**결정 기록 ② 같은 조합은 DB에서 먼저 찾고, 없을 때만 AI를 부른다**

| 항목 | 내용 |
|---|---|
| 상황 | 조합마다 AI를 부르면 토큰이 낭비되고 5초를 맞추기도 어려움. 목표 4번은 "저장된 조합 재요청 시 AI 호출 0회". 방향성이 다르면 같은 단어여도 결과가 달라야 함 |
| 선택지 | ① 매번 AI 호출 ② DB를 먼저 조회하고 없을 때만 AI 호출 · 저장 ③ 모든 조합을 미리 생성 (카테고리당 단어 100개면 161,700개라 비현실적) |
| 결정 | ② 조합 키 = 카테고리 + 정렬한 단어 3개 + 방향성. 키에 유일 제약을 걸어 동시에 들어와도 한 건만 저장, AI 실패 결과는 저장하지 않음 |
| 이유 | 목표 4번을 직접 충족하고, 저장된 조합은 DB 조회만 하므로 응답도 빠름. 방향성을 키에 넣어야 다른 방향의 결과가 재사용되지 않음 |
| 감수한 단점 | 같은 조합이면 항상 같은 결과라 새로움이 떨어짐('새로 생성' 허용 여부 미정). 부적절한 결과가 저장되면 반복 노출되므로 신고 · 숨김 장치 필요. 처음 나온 조합은 최대 5초를 기다림 |
| 결정한 사람 (A) | 지태웅 |

**이번 주에 정리한 것**: 4주차 기획서("공개 범위를 사용자가 선택")와 5주차 공유 시트("범위 설정 화면 없음")가 어긋났던 것을, '링크 복사'와 '피드에 올리기' 두 버튼이 공개 범위 선택을 대신하는 것으로 정리했습니다.

**다음 주까지 정할 것**

- React Native · Node.js · SQL 담당자와 주차별 역할 배정
- '새로 생성' 허용 여부 (허용하면 조합 키를 "조합 키 + 버전"으로 변경)
- 조합 키에서 단어 순서를 무시할지 (기획서 결정 요청 항목)
- Gemini 모델 버전 · 무료 사용량, 서버 호스팅 · DB 서비스와 리전
- 신고 화면을 만들지, 관리자가 DB에서 직접 숨길지
